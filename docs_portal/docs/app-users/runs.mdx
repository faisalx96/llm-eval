# Runs, Metrics, And Traces

Runs are the main evidence object in the qym app. A run records what was evaluated, which dataset items were used, what the system produced, how metrics scored those outputs, and what review state was applied afterward.

## Run list

Use the run list to find the right evaluation before opening details.

| Field | Meaning |
|-------|---------|
| Status | Whether the run is waiting, active, complete, failed, stopped, submitted, approved, or rejected. |
| Task | The evaluated workflow or product behavior. |
| Dataset | The item set used for the evaluation. |
| Model | The model or model label associated with the run when available. |
| Metrics | The scoring methods applied to each output. |
| Owner | The team member, service, or source that created the run. |
| Time | When the run started or completed. |

## Run detail

On a run detail page, inspect in this order:

1. Status and total item count.
2. Aggregate metric summary.
3. Failed, errored, or low-scoring items.
4. Item metadata such as domain, difficulty, risk, or source.
5. Trace links for rows that need deeper debugging.
6. Review notes, corrections, and approval state.

## Item rows

Each item row usually includes:

- the input being evaluated;
- the expected value or reference answer when one exists;
- the actual output;
- per-metric score and label;
- error details when execution or scoring failed;
- metadata that helps filter failures;
- trace or span links when tracing is available.

## Comparisons

Use comparisons when deciding whether a candidate run is better than a baseline. Compare runs that use the same or intentionally comparable datasets, then focus on rows where scores changed.

Good comparison questions:

- Which items improved?
- Which items regressed?
- Did the same item IDs exist in both runs?
- Did metric definitions, model labels, or dataset versions change?
- Are regressions concentrated in one domain, risk level, or difficulty band?

## Traces

Traces explain how a single item was produced. Use them after the item output or metric score raises a question.

Trace views are most useful for:

- slow items;
- tool or retrieval failures;
- unexpected model outputs;
- missing context;
- debugging why an output passed or failed a metric.
