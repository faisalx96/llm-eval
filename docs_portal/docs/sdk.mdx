# SDK

The SDK is the primary qym implementation interface. Use it when Python code should own the evaluation loop: application services, notebooks, workers, scheduled jobs, CI test harnesses, internal tools, or product-specific wrappers.

The CLI is a secondary launcher around the same concepts. Learn the SDK model first, then use the CLI when a shell interface is better for automation.

## High-Level Model

The SDK evaluates a task against a dataset and scores each output with metrics.

```text
dataset item -> task function -> output -> metrics -> result artifact
                                      -> optional traces
                                      -> optional platform stream
                                      -> optional wrapper progress callback
```

Use the SDK when you need control over task functions, dataset objects, metric callables, progress callbacks, observers, tracing, artifact handling, or integration with your own service state.

## Detailed Behavior

An SDK run can:

- load a dataset from `CsvDataset`, another local dataset object, or a Langfuse dataset name;
- call sync or async task functions once per item;
- match dictionary inputs to Python task parameters;
- pass model metadata such as `model_name`, `model`, or trace context when the task accepts it;
- compute built-in metrics, custom callables, and LLM judge metrics;
- enforce task and metric timeouts;
- retry task failures;
- checkpoint long runs and resume from saved files;
- save artifacts under `qym_results/` or a configured output directory;
- run one model, many models, or many run specs;
- emit `ProgressSnapshot` updates through `progress_callback`;
- support advanced lifecycle observers through `EvaluationObserver`;
- create OpenTelemetry spans and optional Phoenix exports;
- stream runs, item events, metrics, and traces to the qym platform when credentials are configured.

The core API is `Evaluator`. Most developers should start there before using lower-level modules.

```python
from qym import Evaluator

results = Evaluator(
    task=my_task,
    dataset=my_dataset,
    metrics=["exact_match"],
).run()
```

## For Developers

When embedding qym in another service, decide these integration points explicitly:

| Concern | Recommended Choice |
|---------|--------------------|
| Progress in your own UI | Use `progress_callback` or `EvaluationObserver`. |
| Shared platform visibility | Set `QYM_PLATFORM_URL` and `QYM_API_KEY`. |
| Offline execution | Use `CsvDataset` and upload artifacts later. |
| Semantic scoring | Add judge metrics after deterministic metrics work. |
| CI automation | Prefer Python when tests need internal state; use CLI `--json` when a shell boundary is required. |
| Multi-model evaluation | Use `model=[...]` or multi-run config depending on whether only the model changes. |
| Shell execution | Use the CLI after the Python task and dataset shape are stable. |

Keep task functions small and deterministic from qym's point of view: external clients, prompts, and credentials can live outside the task, but the task should clearly accept an item input and return the output you want to score. Treat configuration as part of the run contract; record non-secret version labels in `run_metadata`.
