# Local Monorepo Development

Use this workflow only when you are modifying qym itself.

SDK consumers should install from PyPI instead:

```bash
pip install qym
```

## Editable install

From the repository root:

```bash
pip install -e packages/sdk[dev] -e packages/platform
```

Use this when changes in `packages/sdk` or `packages/platform` need to be imported immediately by local Python processes.

## Run platform locally for development

On first run, create the compose env file from the template (the committed defaults suit local development):

```bash
cp docker/.env.template docker/.env
docker compose -f docker/docker-compose.yml -f docker/docker-compose.dev.yml --env-file docker/.env up --build
```

Use the development compose file when iterating on platform APIs, static assets, docs serving, or integration behavior. Do not use development convenience settings as a production hardening model.

## Tests and checks

Run targeted tests while iterating:

```bash
pytest tests/sdk -q
pytest tests/platform -q
```

Run the broader suite before handing off a change:

```bash
pytest -q
```

Format and type-check SDK changes when relevant:

```bash
black .
isort .
mypy packages/sdk/qym
```

## Migrations

When platform models or schema behavior changes, add or update migrations under `packages/platform/qym_platform/migrations`.

Manual migration command for local contributor validation:

```bash
alembic -c packages/platform/qym_platform/migrations/alembic.ini upgrade head
```

Production deployments should use their configured deployment entrypoint or release process.

## Contributor rules

- Keep SDK and platform package boundaries clear.
- Do not commit local `.env` files or secrets.
- Do not treat generated docs or fallback docs as the source of truth when Docusaurus docs exist.
- Keep App User docs free of development commands.
- Keep Developer docs PyPI-first unless a page is explicitly contributor-only.
