# Documentation Audit

This page tracks what the docs portal covers well, what is thin, and what should be written next. Use it as the working backlog for documentation quality.

## High-Level Status

The portal has the right top-level sections: Getting Started, SDK, CLI, API, Examples, Deploy & Operate, Troubleshooting, and Concepts. The generated API and CLI references give exact endpoint and command surfaces.

The main gap is depth. Several pages are currently navigational stubs rather than developer guides. Developer-facing pages should consistently include:

1. A high-level overview that explains when to use the feature.
2. Detailed behavior and contracts, including inputs, outputs, defaults, and failure modes.
3. A developer implementation section with code, commands, integration patterns, and gotchas.

## Documentation Standard

Each non-reference page should use this shape:

```md
# Page Title

Short explanation of who should use this page and why.

## High-Level Model

Conceptual explanation and when to use the feature.

## Detailed Behavior

Inputs, outputs, defaults, data shapes, lifecycle, and edge cases.

## For Developers

Code examples, command examples, integration patterns, failure handling, and testing guidance.

## Troubleshooting

Common symptoms and concrete fixes.

## Related Docs

Links to adjacent pages.
```

Reference pages can stay generated and terse, but every important generated surface should have a hand-written workflow guide nearby.
