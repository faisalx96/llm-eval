# Platform Streaming

Platform streaming is the SDK-to-platform path that makes a local evaluation visible in the shared qym dashboard while it is still running.

Use this page when you are building or debugging a developer workflow that launches qym evaluations from Python, CI, notebooks, queue workers, or internal services.

## Mental model

An SDK run has three outputs:

- **Local result artifacts** under `qym_results/`.
- **Platform events** sent to the qym platform when `QYM_BASE_URL` and `QYM_API_KEY` are configured.
- **Optional wrapper progress** through `progress_callback` when your own app needs local progress updates.

Platform streaming is not required for local evaluation. If the platform is unavailable, qym still runs the evaluation and saves local artifacts.

## Quick start

Set platform connectivity before starting the run:

```bash
export QYM_BASE_URL=https://qym.example.com
export QYM_API_KEY=<your-api-key>
```

Then run normally:

```python
from qym import Evaluator

results = Evaluator(
    task=my_task,
    dataset=my_dataset,
    metrics=["exact_match"],
).run()
```

When the run starts, the SDK creates a platform run, opens a background event streamer, and emits run/item/metric/trace updates to the platform. The platform dashboard uses those events for live status, progress percentages, item rows, metric scores, traces, and final run state.

## Configuration

| Variable | Required | Purpose |
|----------|----------|---------|
| `QYM_BASE_URL` | Yes for streaming | Base URL of the qym platform. |
| `QYM_API_KEY` | Yes for authenticated ingestion | API key created from the platform profile page. |
| `QYM_PLATFORM_DEBUG` | Optional | Enables SDK-side debug logging for platform streaming. |

You can also provide platform values through evaluator config when embedding qym in another Python service:

```python
results = Evaluator(
    task=my_task,
    dataset=my_dataset,
    metrics=["exact_match"],
    config={
        "platform_url": "https://qym.example.com",
        "platform_api_key": "...",
    },
).run()
```

## What the SDK sends

Most developers should use `Evaluator` or the qym CLI and let the SDK handle platform transport. If you are debugging or building platform-compatible tooling, the flow is:

1. Create a run:

```text
POST /v1/runs
Content-Type: application/json
Authorization: Bearer <api-key>
```

The request includes `external_run_id`, `task`, `dataset`, `model`, `metrics`, `run_metadata`, and `run_config`. The platform returns a platform `run_id` and `live_url`.

2. Stream newline-delimited JSON events to that run:

```text
POST /v1/runs/{run_id}/events
Content-Type: application/x-ndjson
Authorization: Bearer <api-key>
```

Every event has a common envelope:

```json
{
  "schema_version": 1,
  "event_id": "uuid",
  "sequence": 1,
  "sent_at": "2026-04-24T12:00:00Z",
  "type": "item_completed",
  "run_id": "platform-run-id",
  "payload": {}
}
```

Important fields:

| Field | Meaning |
|-------|---------|
| `event_id` | Idempotency key for deduplication. |
| `sequence` | Per-run event order assigned by the SDK. |
| `type` | Event name, such as `run_started` or `metric_scored`. |
| `payload` | Event-specific data. |

## Event lifecycle

A typical successful item flows like this:

```text
run_started
item_started
item_attempt_started
item_attempt_finished
metric_scored
item_completed
run_completed
```

A failed item emits `item_failed` instead of `item_completed`.

The SDK may also emit:

| Event | Purpose |
|-------|---------|
| `run_heartbeat` | Keeps active runs fresh even during long LLM calls. |
| `metadata_update` | Adds metadata discovered after run start, such as Langfuse run URLs. |
| `span_completed` | Sends OpenTelemetry span data for trace viewing in the platform. |

## Common event payloads

`run_started` includes run identity and configuration:

```json
{
  "external_run_id": "my-run-name",
  "task": "qa_task",
  "dataset": "qa.csv",
  "model": "gpt-4o-mini",
  "metrics": ["exact_match"],
  "total_items": 100,
  "run_metadata": {"team": "search"},
  "run_config": {"max_concurrency": 10, "timeout": 300},
  "started_at": "2026-04-24T12:00:00Z"
}
```

`item_started` includes the input and expected value:

```json
{
  "item_id": "row_1",
  "index": 0,
  "input": "What is qym?",
  "expected": "An evaluation framework",
  "item_metadata": {"difficulty": "easy"}
}
```

`metric_scored` sends one metric result:

```json
{
  "item_id": "row_1",
  "metric_name": "exact_match",
  "score_numeric": 1.0,
  "score_raw": {"score": 1.0},
  "meta": {},
  "label": "pass",
  "explanation": null
}
```

`item_completed` finalizes an item:

```json
{
  "item_id": "row_1",
  "index": 0,
  "output": "An evaluation framework",
  "latency_ms": 412.0,
  "trace_id": "trace-id",
  "trace_url": "https://...",
  "retry_count": 0
}
```

`run_completed` finalizes the run:

```json
{
  "ended_at": "2026-04-24T12:05:00Z",
  "final_status": "COMPLETED",
  "summary": {
    "total_items": 100,
    "success_count": 98,
    "error_count": 2
  }
}
```

Final status can be `COMPLETED`, `FAILED`, or `STOPPED`.

## Progress hooks for wrappers

Platform streaming and SDK progress hooks are complementary.

Use platform streaming when the run should appear in the shared qym platform.

Use `progress_callback` when your own wrapper also needs local progress: for example, updating an internal job table, websocket, notebook cell, CI annotation, or queue task state.

For multi-run evaluations, the callback gets a `run_matrix` snapshot before individual runs start. Use it to create pending rows in your own UI. The matrix contains `total_items` when qym can resolve the dataset up front, and `qym_url=None` initially because platform URLs are created per run. When each run starts, its `run_start` snapshot includes `run_info["qym_url"]`, `run_info["html_url"]`, and `run_info["platform_run_id"]`.

```python
from qym import Evaluator, ProgressSnapshot

def on_progress(snapshot: ProgressSnapshot):
    if snapshot.event == "run_matrix":
        for run in snapshot.run_matrix or []:
            publish_to_internal_job_store(
                run_id=run["run_id"],
                event="pending",
                model=run.get("model"),
                total_items=run.get("total_items"),
                qym_url=run.get("qym_url"),
            )
        return

    if snapshot.event == "run_start":
        publish_to_internal_job_store(
            run_id=snapshot.run_id,
            event=snapshot.event,
            qym_url=(snapshot.run_info or {}).get("qym_url"),
            platform_run_id=(snapshot.run_info or {}).get("platform_run_id"),
        )
        return

    publish_to_internal_job_store(
        run_id=snapshot.run_id,
        event=snapshot.event,
        finished=snapshot.finished,
        total=snapshot.total_items,
        percent=snapshot.percent_complete,
        failed=snapshot.failed,
        metric_duration_ms=(snapshot.metadata or {}).get("duration_ms"),
        task_time_ms=(snapshot.result or {}).get("task_time_ms"),
        total_time_ms=(snapshot.result or {}).get("total_time_ms"),
    )

results = Evaluator(
    task=my_task,
    dataset=my_dataset,
    metrics=["exact_match"],
    progress_callback=on_progress,
).run(show_tui=False)
```

The callback does not replace platform streaming. Keep `QYM_BASE_URL` and `QYM_API_KEY` configured when the run should appear in qym.

For `Evaluator.run_parallel(...)`, pass `observer=ProgressCallbackObserver(on_progress)` to receive the same `ProgressSnapshot` events. The `progress_callback` shortcut is available on the `Evaluator(...)` constructor.

Live metric snapshots include metric timing metadata when measured: `duration_ms`, `duration_seconds`, `started_at_ms`, `completed_at_ms`, and `status`. Item completion snapshots include task latency and total item latency in `result`, including `task_time_ms`, `total_time_ms`, item/task timestamps, retry count, trace fields, and final scores.

## Advanced observer integration

Use `progress_callback` for simple progress updates. Use `EvaluationObserver` when your integration needs named lifecycle hooks and event-specific handling.

```python
from qym import EvaluationObserver, Evaluator

class OurObserver(EvaluationObserver):
    def on_run_matrix(self, matrix_id, runs, total_runs):
        create_pending_run_rows(matrix_id=matrix_id, runs=runs, total_runs=total_runs)

    def on_run_start(self, run_id, run_info, total_items, metrics):
        create_run_record(
            run_id=run_id,
            total_items=total_items,
            metrics=metrics,
            metadata=run_info,
            qym_url=run_info.get("qym_url"),
            platform_run_id=run_info.get("platform_run_id"),
        )

    def on_item_start(self, run_id, item_index, payload=None):
        mark_item_running(run_id, item_index, payload)

    def on_metric_result(self, run_id, item_index, metric_name, score, metadata=None):
        store_metric_result(
            run_id=run_id,
            item_index=item_index,
            metric_name=metric_name,
            score=score,
            metadata=metadata,
        )

    def on_item_complete(self, run_id, item_index, result):
        mark_item_complete(run_id, item_index, result)

    def on_item_error(self, run_id, item_index, error):
        mark_item_failed(run_id, item_index, error)

    def on_run_complete(self, run_id, result_summary):
        finalize_run(run_id, result_summary)

results = Evaluator(
    task=my_task,
    dataset=my_dataset,
    metrics=["exact_match"],
    observer=OurObserver(),
).run(show_tui=False)
```

The observer API is local to the SDK process. It does not send data to the qym platform by itself. Keep platform credentials configured when the run should also stream into the shared dashboard.

## Reliability behavior

The SDK streams events in a background thread and batches them for low-latency updates.

Behavior to know:

- Events are sent as NDJSON batches.
- The SDK retries failed batches.
- If a batch keeps failing, the SDK falls back to per-event sends so one bad event does not block the rest.
- Heartbeats are emitted during long runs.
- On shutdown, the SDK flushes queued events before closing the streamer.
- `run_completed` is sent synchronously so the platform is less likely to leave a completed or interrupted run stuck as `RUNNING`.
- Ctrl+C attempts to send final status `STOPPED`.

The platform should deduplicate by `(run_id, event_id)` and use `sequence` to reason about event order.

## Developer patterns

### Python service wrapper

Use `progress_callback` for your service state and platform streaming for shared qym visibility:

```python
def launch_eval(job_id: str):
    def on_progress(snapshot):
        jobs.update(
            job_id,
            qym_run_id=snapshot.run_id,
            status=snapshot.event,
            progress=snapshot.percent_complete,
            finished=snapshot.finished,
            total=snapshot.total_items,
            failed=snapshot.failed,
        )

    return Evaluator(
        task=my_task,
        dataset=my_dataset,
        metrics=["exact_match"],
        config={"run_metadata": {"job_id": job_id}},
        progress_callback=on_progress,
    ).run(show_tui=False)
```

### CI

Use `qym config check --json` before starting a run that is expected to stream:

```bash
qym config check --json
qym run create --task-file eval_task.py --task-function run \
  --dataset qa-set --metrics exact_match
```

If `qym config check` fails, decide whether CI should fail fast or run local-only and upload artifacts later.

### Offline or air-gapped runs

Skip streaming when the runtime cannot reach the platform. Let qym write local artifacts, then upload later:

```bash
qym submit --file qym_results/.../run.csv --task my_task --dataset my_dataset
```

## Troubleshooting

### Run does not appear in the platform

Check:

- `QYM_BASE_URL` points to the platform base URL.
- `QYM_API_KEY` is set in the same process that launches the SDK.
- The API key belongs to a user allowed to ingest runs.
- `qym config check --json` succeeds.
- The platform can reach its database and migrations are current.

### Run appears but progress is stale

Check:

- The SDK process is still alive.
- Long task calls are not blocking forever.
- `run_heartbeat` events are reaching the platform.
- `total_items` is present in run metadata.
- The platform worker/API logs are not rejecting events.

### Run remains `RUNNING` after interruption

The SDK attempts to send `STOPPED` on Ctrl+C or termination. If the process is killed hard, the final event may not be sent. Platform stale-run recovery should use heartbeat age to identify abandoned runs.

### Metrics are missing or incomplete

Metric events are emitted separately from item completion. Check that:

- The metric function actually returned a value.
- The metric event was not rejected by the platform.
- The run was not interrupted before the SDK could flush queued events.

### My wrapper needs progress but not platform storage

Use `progress_callback` without `QYM_BASE_URL` or `QYM_API_KEY`. The callback is local SDK progress; platform streaming is only enabled when platform credentials are configured.
