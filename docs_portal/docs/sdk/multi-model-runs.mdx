# Multi-Model And Multi-Run Evaluations

Use multi-model and multi-run evaluations when one task/model pair is not enough evidence.

## High-Level Model

There are two common comparison modes:

| Mode | Use When |
|------|----------|
| Multi-model evaluator | Same task, same dataset, same metrics, different models. |
| Multi-run config | Different tasks, datasets, metrics, configs, or model groups. |

The platform comparison views work best when runs share dataset item identities.

## Detailed Behavior

### Multi-Model Evaluator

Use `model=[...]` when only the model changes.

```python
from qym import Evaluator

def answer(question, model_name="gpt-4o-mini"):
    return call_llm(model=model_name, prompt=question)

results = Evaluator(
    task=answer,
    dataset=my_dataset,
    metrics=["exact_match", "relevance"],
    model=["gpt-4o-mini", "gpt-4.1-mini"],
).run()
```

qym passes `model_name` or `model` into your task when your function accepts it.

### Task Signature

```python
def task(question, model_name="gpt-4o-mini"):
    return call_llm(model=model_name, prompt=question)
```

or:

```python
def task(question, model="gpt-4o-mini"):
    return call_llm(model=model, prompt=question)
```

### CLI Multi-Run Config

Use `--runs-config` when run definitions differ.

```bash
qym run create --runs-config experiments.json
```

Use this for:

- different datasets
- different metric sets
- different task functions
- different concurrency or timeout settings
- multi-model batches with independent names

### Concurrency

Multi-model evaluation can multiply effective concurrency:

```text
effective work = number of models * max_concurrency
```

If you evaluate 4 models with `max_concurrency=10`, provider traffic can look like 40 parallel item calls. Tune this deliberately.

### Progress Shape For Wrappers

Wrappers and custom UIs can learn the full multi-run shape before any individual run starts by using `progress_callback` on a multi-model `Evaluator`, or `observer=ProgressCallbackObserver(...)` with `Evaluator.run_parallel`.

```python
from qym import Evaluator, ProgressCallbackObserver, ProgressSnapshot

def on_progress(snapshot: ProgressSnapshot):
    if snapshot.event == "run_matrix":
        for run in snapshot.run_matrix or []:
            create_pending_row(
                run_id=run["run_id"],
                display_name=run["display_name"],
                model=run.get("model"),
                metrics=run["metrics"],
                total_items=run.get("total_items"),
                qym_url=run.get("qym_url"),  # None until run_start
            )
        return

    if snapshot.event == "run_start":
        update_pending_row(
            run_id=snapshot.run_id,
            qym_url=(snapshot.run_info or {}).get("qym_url"),
            platform_run_id=(snapshot.run_info or {}).get("platform_run_id"),
        )

results = Evaluator.run_parallel(
    runs=runs_config,
    observer=ProgressCallbackObserver(on_progress),
)
```

The `run_matrix` event contains all expanded runs, including entries created from each `models` list. URLs are patched later through each run's `run_start` event because the SDK receives `qym_url` only after that run has been created on the platform.

`total_items` is included in matrix rows when qym can resolve the dataset before execution. Per-run `run_start(total_items=...)` remains the exact source of truth. Live metric snapshots include metric duration metadata, and item completion snapshots include both task latency and total item latency.

## For Developers

### Comparison-Ready Dataset

Use stable item IDs. Platform comparison depends on aligning items across runs.

Good:

```csv
id,question,answer,difficulty
qa-001,What is 2+2?,4,easy
```

Risky:

```csv
question,answer
What is 2+2?,4
```

Generated IDs can work for stable CSV content, but explicit IDs are safer.

### Naming Strategy

Include task and model in run metadata, not just the run name.

```python
config={
    "task_name": "support-rag",
    "run_metadata": {
        "prompt_version": "v12",
        "retriever": "hybrid-v3",
    },
}
```

### Common Mistakes

| Mistake | Impact | Fix |
|---------|--------|-----|
| Hardcoded model inside task | `model=[...]` appears to run but all calls use the same model. | Accept `model_name` and route with it. |
| Too much parallelism | Provider throttling and noisy failures. | Lower `max_concurrency` or limit parallel runs. |
| Different item IDs across runs | Platform comparison cannot align items reliably. | Use stable `id_col`. |
| Different metric names | Comparison table becomes sparse. | Keep shared metrics for runs you intend to compare. |
