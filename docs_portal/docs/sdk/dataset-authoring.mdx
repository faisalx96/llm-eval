# Dataset Authoring

Datasets are the contract between the behavior you care about and the metric evidence qym produces. Weak datasets produce misleading evaluation results even when the SDK is configured correctly.

## High-Level Model

Each dataset item should provide:

| Field | Purpose |
|-------|---------|
| `id` | Stable item identity for resume, comparison, and review. |
| `input` | The value passed into the task function. |
| `expected_output` | The reference answer or target behavior for metrics. |
| `metadata` | Tags used for filtering, grouping, and analysis. |

The task reads `input`. Metrics compare `output` to `expected_output` and may use `metadata` or input fields for context.

## Detailed Behavior

### CSV Datasets

Use `CsvDataset` for local, offline, and air-gapped evaluation.

```python
from qym import CsvDataset, Evaluator

dataset = CsvDataset(
    "datasets/qa.csv",
    input_col="question",
    expected_col="answer",
    id_col="id",
    metadata_cols=["difficulty", "domain", "source"],
)
```

Example CSV:

```csv
id,question,answer,difficulty,domain,source
qa-001,What is 2+2?,4,easy,math,smoke
qa-002,What is qym?,An evaluation framework,medium,llm-eval,docs
```

If `id_col` is omitted, qym generates stable-ish CSV IDs from item content and a duplicate counter. Prefer explicit IDs for datasets that will be reviewed, resumed, or compared.

### JSON Cells In CSV

CSV cells that start with `{` or `[` are parsed as JSON. Other values remain strings.

```csv
id,input,expected_output,metadata
case-1,"{""question"": ""What is qym?"", ""context"": ""LLM eval""}","An evaluation framework","{""difficulty"": ""easy""}"
```

This lets task functions accept structured fields:

```python
def task(question, context):
    return call_llm(f"{context}\n{question}")
```

### Langfuse Datasets

Use a Langfuse dataset name when the dataset is centrally managed:

```python
results = Evaluator(
    task=my_task,
    dataset="production-qa-regression",
    metrics=["exact_match"],
).run()
```

Langfuse dataset usage requires Langfuse credentials. CSV datasets do not.

### Metadata Strategy

Good metadata makes the platform useful.

Recommended metadata:

- `domain`
- `difficulty`
- `source`
- `language`
- `customer_segment`
- `prompt_version`
- `retrieval_type`
- `expected_tool`
- `risk_level`

Avoid metadata fields that are unique for every row unless they are identifiers. Too many unique values make breakdowns noisy.

## For Developers

### Dataset Quality Checklist

- Every item tests one clear behavior.
- IDs are stable across commits and reruns.
- Expected outputs are specific enough for deterministic metrics.
- Metadata supports the slices reviewers actually care about.
- The dataset has a small smoke subset for fast local checks.
- Large regression datasets are versioned and reviewed.
- Ambiguous items have notes in metadata or expected output.

### Task Signature Alignment

For scalar CSV input:

```csv
id,question,answer
1,What is 2+2?,4
```

```python
def task(question):
    return call_llm(question)
```

For structured JSON input:

```csv
id,input,expected_output
1,"{""question"": ""What is 2+2?"", ""context"": ""math""}",4
```

```python
def task(question, context):
    return call_llm(f"{context}: {question}")
```

### Common Mistakes

| Mistake | Impact | Fix |
|---------|--------|-----|
| Missing expected output | Deterministic metrics cannot score correctly. | Add `expected_col` or use metrics that do not require expected output. |
| Unstable IDs | Resume and comparison become noisy. | Add explicit `id_col`. |
| Overly broad expected answers | Exact metrics fail even when output is acceptable. | Use semantic judge or improve expected value. |
| Metadata absent | Platform charts and analysis cannot segment failures. | Add useful metadata columns. |
| Mixed task types in one dataset | Metrics become incoherent. | Split datasets by task. |
