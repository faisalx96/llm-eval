# API Ingestion Guide

Use this page when you need to ingest runs into the platform without using the Python SDK. If Python can run in your environment, prefer the SDK because it already handles retries, heartbeats, final status, traces, and local artifacts.

## High-Level Model

There are two ingestion paths:

| Path | Use When |
|------|----------|
| Stream events | You want a live run in the platform while work is executing. |
| Upload artifact | The run already finished elsewhere or happened offline. |

The SDK uses the streaming path internally.

## Detailed Behavior

### Create A Run

```text
POST /v1/runs
Authorization: Bearer <api-key>
Content-Type: application/json
```

Payload:

```json
{
  "external_run_id": "qa-smoke-001",
  "task": "qa_task",
  "dataset": "qa.csv",
  "model": "gpt-4o-mini",
  "metrics": ["exact_match"],
  "run_metadata": {"team": "search"},
  "run_config": {"max_concurrency": 10}
}
```

Response includes:

```json
{
  "run_id": "platform-run-id",
  "live_url": "https://qym.example.com/run/platform-run-id"
}
```

### Stream Events

```text
POST /v1/runs/{run_id}/events
Authorization: Bearer <api-key>
Content-Type: application/x-ndjson
```

Each line is one event:

```json
{"schema_version":1,"event_id":"uuid","sequence":1,"sent_at":"2026-04-24T12:00:00Z","type":"run_started","run_id":"platform-run-id","payload":{"task":"qa_task","dataset":"qa.csv","metrics":["exact_match"],"started_at":"2026-04-24T12:00:00Z"}}
```

Recommended event order:

```text
run_started
item_started
item_attempt_started
item_attempt_finished
metric_scored
item_completed
run_completed
```

For failures, emit `item_failed`.

### Upload Artifact

```text
POST /v1/runs:upload
Authorization: Bearer <api-key>
Content-Type: multipart/form-data
```

Use this for saved CSV/JSON/XLSX results from qym or another compatible process.

## For Developers

### Idempotency

Generate a unique `event_id` for every event. If you retry the same event, reuse the same `event_id`.

The platform should deduplicate by:

```text
(run_id, event_id)
```

### Ordering

Increment `sequence` per run.

```text
1, 2, 3, ...
```

The platform can use `sequence` for ordering and stale-event detection. Do not reset sequence numbers in the middle of a run.

### Heartbeats

For long-running jobs, emit heartbeats:

```json
{
  "type": "run_heartbeat",
  "payload": {"heartbeat_at": "2026-04-24T12:01:00Z"}
}
```

Heartbeats help the platform distinguish active long runs from abandoned ones.

### Finalization

Always send `run_completed` with one of:

- `COMPLETED`
- `FAILED`
- `STOPPED`

If finalization is missing, the platform may show the run as `RUNNING` until stale-run recovery handles it.

### Common Mistakes

| Mistake | Impact | Fix |
|---------|--------|-----|
| Creating item events before creating run | Events have nowhere to attach. | Call `POST /v1/runs` first. |
| Reusing event IDs for different events | Legitimate events may be deduped. | Generate new UUID per event. |
| Not sending final event | Run can stay `RUNNING`. | Always send `run_completed`. |
| Sending scores after item completion only sometimes | Metrics look incomplete. | Emit one `metric_scored` per metric. |
| No stable item IDs | Review and comparison are harder. | Use deterministic item IDs. |
