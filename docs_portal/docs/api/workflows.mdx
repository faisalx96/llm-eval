# Common API Workflows

Use the API directly when the CLI and SDK do not give enough control. For most developer workflows, prefer SDK or CLI first.

## High-Level Model

The platform API has two broad surfaces:

- `/v1/...` for ingestion, auth, users, projects, and automation-friendly operations.
- `/api/...` for dashboard-oriented run review, comparison, corrections, trace access, and analysis.

The generated reference gives exact endpoint parameters. This page gives recommended request sequences.

## Ingest a run

### Stream incrementally

Use this when you are building platform-compatible ingestion outside the SDK.

1. Create the run.

```text
POST /v1/runs
Authorization: Bearer <api-key>
```

2. Stream events.

```text
POST /v1/runs/{run_id}/events
Content-Type: application/x-ndjson
```

3. End with `run_completed`.

4. Inspect the run through `/api/runs/{run_id}` or the UI.

### Upload a completed artifact

Use this when the run happened offline or in another environment.

```text
POST /v1/runs:upload
Content-Type: multipart/form-data
```

Send the saved CSV/JSON/XLSX artifact plus task and dataset metadata.

## Review a run

1. Resolve the target run ID.
2. Fetch the run details and failed items.
3. Trigger analysis if you need clustered failure explanations.
4. Approve, reject, or correct outcomes as needed.

## Provision a project

1. Create the project.
2. Add members.
3. Create project-scoped API keys.
4. Hand the credentials to SDK or pipeline clients.

## For Developers

### Direct Event Ingestion

Only build direct event ingestion if the SDK cannot run in your environment. If Python can run there, use the SDK because it already handles event order, retries, final status, heartbeats, traces, and local artifacts.

Minimal event envelope:

```json
{
  "schema_version": 1,
  "event_id": "uuid",
  "sequence": 1,
  "sent_at": "2026-04-24T12:00:00Z",
  "type": "run_started",
  "run_id": "platform-run-id",
  "payload": {}
}
```

### Review Automation

For review tools, fetch run details first, then apply narrow changes:

```text
GET /api/runs/{run_id}
GET /api/runs/{run_id}/corrections
POST /api/corrections/{correction_id}/approve
POST /api/corrections/{correction_id}/reject
```

### Analysis Automation

Trigger analysis only after a run has enough failed or low-scoring items to inspect:

```text
POST /api/runs/{run_id}/analyze
GET /api/runs/{run_id}
```

## Troubleshooting

| Symptom | Likely Cause | Fix |
|---------|--------------|-----|
| `401` | Missing or invalid bearer token. | Create a new API key and pass `Authorization: Bearer ...`. |
| `403` | User lacks access to the project/run. | Check org membership, project membership, or platform visibility rules. |
| Run appears without items | Events were not posted or were rejected. | Inspect ingestion response and platform logs. |
| Run stuck as running | Final `run_completed` event was not delivered. | Send final status or rely on heartbeat-based stale recovery. |
